# reMarkable Paper Pro Move 设备端 EPUB 查词（中/英）可行性核查

> 2026-08-25，`dict-lookup-recon` 分支。针对"划词查字典"的一份外部分析（三路线：KOReader / Rust 生词本 / LD_PRELOAD 劫持 UI）做**逐条对表本项目已坐实的事实**。
> 结论：外部分析对**通用 reMarkable** 大体成立，但三条路线的可能性排序对**这台 Move + 本项目**几乎全反了。

## 一、结论先行（修正外部分析的可能性排序）

| 路线 | 外部分析判定 | **本项目实况修正** | 依据 |
|---|---|---|---|
| ① KOReader | 极高·社区主流 | **已判死** | Move 上 KOReader 两条路全堵 |
| ② 异步生词本 | 100% 可行·要新写 Rust | **核心动作已在生产跑**，是最小增量 | 荧光笔读回文字+颜色已是生产管线（`pkm/src/cardhl.rs`） |
| ③ 劫持原生 UI 弹窗 | 极低·地狱级·LD_PRELOAD | 注入机制本项目**日常在用**（xovi+qmldiff，非 LD_PRELOAD）；但**前提「选中文本事件」大概率不存在**，且弹窗覆盖阅读画布够不到 |、、 |

**净判断**：查词在本设备**可行，置信度高**——但可行的形态是**路线二（荧光笔→异步查词写回卡片/生词本）**，不是外部分析暗示的"等 KOReader"或"硬啃 UI 注入"。而且路线二不是"要新写"，是**在已跑通的荧光笔管线上加一个查词步骤**。

## 二、逐条核查

### 路线① KOReader —— 外部分析的最大事实错误

外部分析给"极高·最完美一劳永逸"，并留了个 if：「如果社区适配了彩屏驱动」。**这个 if 在 Move 上已是否定**：

- KOReader 在 Move 上**两条路都堵死**（ 坐实）。Move 不是 rM1/rM2，Toltec/rm2fb 那套彩屏 framebuffer 适配对 Move 的 Gallery 3 屏**不成立**。
- 外部分析自己也点到了这个"特殊阻碍"，但仍给"极高"——**对本设备这是错的**。它描述的是 rM2 生态的现实，不是 Move。

→ **路线①判死，不是"等一等"，是本项目已验过走不通。**

### 路线② 异步生词本 —— 外部分析低估了：核心已建成

外部分析说"延续上回合的 Rust 守护进程……但要新写查词"。实况是**除"查词"外，整条链本项目已在生产运行**：

1. **读回高亮文字**：`pkm/src/cardhl.rs::extract_highlights` 已从 EPUB 页 `.rm` 的 `SceneGlyphItem`(GlyphRange) 读出**高亮文字 + 字符 offset + 颜色**（2026-08-25 真机《13 67》坐实，6 色判色已标定）。外部分析设想的"守护进程提取高亮处底层文本"——**已经在跑**。
2. **颜色分流**：6 支荧光笔已映射 6 固定色槽。查词只要**约定某一色（如 ⚪ Gray「人物/生词」或专设一色）= 生词**，daemon 见该色高亮就查词，其余色照旧归卡片槽。零新概念。
3. **上下文/章节**：`epubindex`（页→章-节名）已在生产，生词的"所在句/章"信息现成。
4. **写回**：`cardnote`/`cardsync` 造笔记本、`/upload` 注入、跨重建保留打字批注——全套已跑通。

**真正要新加的只有一步**：拿到英文单词/中文词 → 查本地词典 → 把释义排进卡片对应槽下（或单独一本《生词本》）。

**触发时机的一个诚实修正**：外部分析说"守护进程监听 `.rm` 修改"。本项目已知 `fswatch` **只在 xochitl 真实存盘时触发**（手动 touch/cp/mv 不触发），且冷启动/存盘后有 debounce。所以它天生是**异步**的（秒级~十几秒延迟），不是实时——这正好符合外部分析路线二的"妥协点"，无需幻想实时。

→ **路线②置信度高，且工作量 = 词典查询 + 排版一步，非从零。**

### 路线③ 劫持原生 UI 实时弹窗 —— 机制会做，但前提可能不存在

外部分析把它定为"极低·地狱级·LD_PRELOAD·改版号就死机"。要分两层看：

- **注入机制没那么可怕**：本项目**不用 LD_PRELOAD**，用官方 xovi 扩展 + qmldiff，已日常向 xochitl 注入 QML（候选栏、设置面板、阅读增强面板全是真机跑通的注入）。"改个版本号就崩"被 `_xovi_shouldLoad` 特征码预检兜住。所以"注入一个 Qt 控件"**本身不是地狱**。
- **但前提大概率不成立**：路线③要"拦截长按选中文本事件"。本项目对该阅读器的已知证据强烈指向——**原生 EPUB 阅读器没有逐词选中手势**：高亮是**画笔（highlighter 笔）划过再吸附到文字行/词**（ 反编译坐实 xochitl 手写分词吸附逻辑），不是 Kindle 式"长按选词弹菜单"。**没有"选中文本"这个事件可拦。**
- **弹窗覆盖阅读画布够不到**：正文渲染在 C++ 的 SceneView tile 增量渲染层，qmldiff/注入的 QML **够不进那一层**（ 判死同源）。注入的 Popup 是独立 QML 层、**只能按 x/y 定位**，要"贴着被查的词浮出来"缺少可靠锚点坐标。

→ **路线③即便硬做，也只能退化成"hook 荧光笔吸附路径(FUN_00f086b0 附近)→ 在固定角落弹一个 Popup"**，脆弱、收益低，且和路线②读的是同一份高亮数据。**不推荐**，除非将来强需求实时反馈再评估。

## 三、推荐路径（路线②的最小落地形态）

**荧光笔查词 → 写回《生词本》/卡片**，骑现有管线：

1. **约定触发色**：选一支荧光笔专作"查词"（建议独立于现 6 色槽语义，或复用 ⚪ Gray）。避免和已有"高亮→卡片槽"语义打架——这条要和现有 `cardhl` 色槽设计对齐后定。
2. **判语种 + 查词**：读回的高亮文字 → 判中/英（简单启发式：含 CJK → 查中英词典查该词；纯拉丁 → 查英中）→ mmap 本地词典查释义。
3. **写回**：释义 + 原句上下文 + 章-节·页号 → 排进该书卡片对应槽下，或单出一本《📔 生词本》笔记本（daemon 汇总本模式，和 🎨/📖/📊 并列）。
4. **异步可接受**：秒级延迟符合 reMarkable "无干扰"哲学，无需实时。

**待离线敲定的小项**（都便宜、不阻塞可行性结论）：
- 触发色与现 6 色槽的语义划分（设计决定，非技术风险）。
- 词典查询的分词粒度：GlyphRange 读回的是"你划过的那一段文字"，英文划一个词 OK；中文要不要做最长匹配分词，取决于是查单字还是查词。
- （可选）ghidra 确认阅读器确无隐藏的选词路径——仅为把路线③彻底钉死，不影响路线②落地。

## 四、词典数据与许可证（实测核实）

沿用本项目纪律：**词典数据不编译进 `.so`，做成独立文件运行时 mmap 只读**（同 rime-ice 词典处理）。

| 词典 | 方向 | 许可证 | 规模 | 备注 |
|---|---|---|---|---|
| **CC-CEDICT** | 中→英 | **CC BY-SA 4.0**（MDBG 官方口径） | ~12.5 万条（2026-08-09 版） | copyleft·署名+相同方式共享；数据独立文件不入 `.so`，署名保留即可 |
| **ECDICT**（skywind3000） | 英→中 | **MIT**（仓库 LICENSE） | 数百万词条，带 BNC/COCA 词频 + 考纲标签 | StarDict/SQLite/CSV 多格式；数据源聚合，个人自用无虞 |

- 两者都适合"独立文件 mmap 只读"，不触碰"GPL/LGPL 数据不入 .so"红线（CC BY-SA、MIT 均非此列，且本就不编译进 .so）。
- **落地前按纪律实测下载各自 `LICENSE` 核对一次**（不凭本文/搜索印象），本表是搜索所得初判、非法律意见。
- 个人自用不分发，与本项目既有 codec/微信读书合规口径一致。

## 五、一句话结论

**能做，置信度高，但形态是"荧光笔划词 → 异步查本地词典 → 写回生词本/卡片"，几乎是现有荧光笔管线加一个查词步骤**；外部分析的"等 KOReader"（本设备已判死）和"实时弹窗劫持 UI"（无选词事件可拦、弹窗够不到画布）都不是本项目该走的路。
