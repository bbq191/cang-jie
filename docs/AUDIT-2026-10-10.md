# 系统代码审计与重构蓝图（2026-10-10）

> 范围：当前 git 仓库内仍在开发的 6 条顶层线——`rmsvc-core/`（含 `epubpkg`）、`shelf/`、`notes/`、`gateway/`（含 `ui/app.js` 前端）、`enhance/`、`packaging/`。不含 `vendor/` 第三方源码本身、`defw/` 逆向产物。
> 基线：分支 `docs/refresh-2026-10-10`，HEAD `80f66fe`。约 4 万行（Rust/C/JS/QML diff/shell）。
> 方法：按目录分 5 路只读审计，每条发现要求 `file:line` 证据；白皮书明写"有意为之"的取舍不计为问题。汇总时对关键结论做了二次抽查（标 ✔）。**本阶段未修改任何代码。**
> 前提说明：仓库此前已做过 6 轮全系统审计，大块重复（OpRegistry、VerifyCache、ChapterStore\<T\>、epubpkg、前端 el()/btn() 等）已消除。本报告只列**仍然存在**的问题，所以总体结论是"结构健康、局部收敛"，而不是"需要大改"。

## 一、总体结论

| 维度 | 评级 | 一句话 |
|---|---|---|
| 分层与服务边界 | **良** | 各服务只写自己的数据目录、跨服务一律走 `SvcClient`；网关代理不含业务知识。 |
| 设计模式使用 | **良（缺失多于滥用）** | 没有发现过度抽象/God 模块；问题集中在**该用类型却用了字符串**（状态、文件夹标识、错误、事件）。 |
| 耦合 | **中** | 主要耦合点只有一个：**"把一份文件投进 xochitl"** 散落在 4 处，各写各的认领判据和文件夹解析。 |
| 重复代码 | **良** | 跨 workspace 8 行窗口真实重复 **0 块**；剩余重复是领域知识级（`.content` 页表、认领逻辑、xovi 胶水、shell rootfs 编辑）。 |
| 前后端复用 | **中下** | 前端与后端之间**没有任何机器校验的契约**：状态枚举、派生判据、书名规范化在 JS 里各镜像一份，已出现显示 bug。 |
| 安全/供应链 | **需立即处理 1 项** | 网关 443 端口的 TLS 依赖 rustls 0.20.9，受 RUSTSEC-2024-0336 影响且该系列无补丁版本。 |

最值得投入的三件事：
1. **P0** 升级 vendored tiny_http 的 rustls 适配层（安全）。
2. **P1** 抽出统一的 `XochitlDelivery` + `upload_and_claim`（消掉 4 套认领逻辑和一个认错书的竞态）。
3. **P1** 建立前后端契约：后端下发派生字段 + 编译期注入常量 + 契约测试。

## 二、问题清单

编号规则：`SEC` 安全、`X` 跨线主题、`CORE` 基座、`SH` 书架、`NT` 笔记、`GW` 网关后端、`FE` 前端/契约、`EN` 系统增强、`PK` 打包。

### 2.1 安全与供应链

**SEC-1【高】网关 HTTPS 使用 rustls 0.20.9，受 RUSTSEC-2024-0336（CVE-2024-32650）影响** ✔
- 证据：`rmsvc-core/Cargo.toml:10` 无条件启用 `tiny_http` 的 `ssl-rustls`；`rmsvc-core/vendor/tiny_http/Cargo.toml:51` 依赖 `rustls 0.20`；`vendor/tiny_http/src/ssl/rustls.rs:13,111` 使用 `rustls::StreamOwned`（公告点名受影响的类型）；`gateway/Cargo.lock` 解析为 `rustls 0.20.9`；网关监听 `0.0.0.0:443`。
- 外部来源：RustSec 公告列出受影响范围含**整个 0.20 系列**，修复版本只有 `≥0.21.11 / ≥0.22.4 / ≥0.23.5`；CVSS 向量 `AV:N/AC:L/PR:N/UI:N/A:H`（握手期间收到 close_notify 时 `complete_io` 死循环）。
- 后果：局域网内任意主机可让网关连接线程空转 CPU，墨水屏设备上直接表现为耗电/发热。
- 置信度：版本受影响 **高**；经 tiny_http 这条路径可触发 **中**（路径与公告一致，未实测）。
- 附带问题：每个 lockfile 同时带两套 TLS 栈（rustls 0.20 + ring 0.16 / rustls 0.23 + ring 0.17，后者来自 ureq），二进制体积与编译时间双份。

**SEC-2【中】CI 不交叉编译 C 扩展，部署失败会回退到仓库里提交的 `.so`**
- 证据：`.github/workflows/ci.yml:57-61` 只跑 host 单测；cross-build job（`ci.yml:95`）已装 aarch64 gcc 但只编 `shelf/build.sh`；`packaging/deploy-xovi-ext.sh:41-49` 构建失败时改用已提交的 `.so`。
- 后果：C 源码改坏/出现警告不会被发现，提交的二进制可能与源码悄悄脱节——这与项目"交叉编译零警告"门槛不符。

**SEC-3【低】CI 只有 shelf 用了 `cargo --locked`，且无漏洞公告扫描**
- 证据：`ci.yml:79` 用了 `--locked`，`ci.yml:72-76,81` 没用。SEC-1 本应由 `cargo audit`/`cargo deny check advisories` 自动发现。

### 2.2 跨线主题（多个模块共同暴露的问题）

**X-1【高】"把文件投进 xochitl"散落 4 处：认领判据各不相同，最弱的一套可能认错书** ✔
- 4 套"上传后认出新文档 uuid"：
  | 位置 | 判据 | 并发保护 |
  |---|---|---|
  | `shelf/.../book-serve/src/import.rs:245-275` | 上传前快照 + 字节相同 | 进程内 `CLAIM` 锁 |
  | `shelf/.../book-serve/src/render_check.rs:56-67` | 时间窗 + 书名/文件名相符，**都不符时取最新一本** | 无 |
  | `notes/services/note-serve/src/publish.rs:186-212` | visibleName + 排除旧候选 | 无 |
  | `rmsvc-core/src/xochitl/mod.rs:150-161` | 占位字节数相等 | — |
- 风险（置信度中）：母版库每本书一条投递线程，直接导入并行运行；`pick` 兜底取最新一本 → `register_comic_margins` 把页边距登记到别人刚投的书上（`render_check.rs:45-46`）。
- 另一已知竞态：`rmsvc-core/src/xochitl/mod.rs:189-193` 注明"设当前文件夹再上传"这对操作只有进程内锁，跨进程（book-serve 与 note-serve）仍会交错，书或笔记本可能落进对方的文件夹。
- 文件夹解析也有两套 ✔：网页「加入」走 `deliver.rs:132-147` 的 `find_folder`（**全库任意层按名字找**，同名取 read_dir 先扫到的，见 `rmsvc-core/src/xochitl/library.rs:63-66`），直接导入走 `ensure_folder_path` 按层用 uuid。10-07 起直接导入会产生多级同名文件夹（如「漫画/卷01」「小说/卷01」），网页选"卷01"时书可能落进某个子文件夹，与 `shelf/docs/传书EPUB线架构.md` §4"网页仍建在根"不符。
- 根因：`Staging` 一身两职（母版库仓储 + xochitl 投递网关），`Importer` 为借投递能力克隆了整个 `Staging`（`import.rs:105-108`）；落库（`deliver.rs:179-207`，每次新起线程、结果写边车）与直接导入（`api.rs:198-232` 拼闭包交给 `import_jobs.rs` 串行，结果只在内存）是两套任务模型。

**X-2【中】xochitl `.content` 页表解析写了两份**
- `shelf/.../book-serve/src/progress.rs:267-284`（`PageMap::parse`）与 `notes/services/ink-serve/src/doc.rs:27-41`（`Content::page_ids`）都实现"取 `cPages.pages` → 按 `idx.value` 排序 → 去掉 deleted"。`progress.rs:234-238` 还手解 `lastOpenedPage`，因为 `rmsvc_core::xochitl::Metadata` 没有该字段。这是 xochitl 文件格式知识，其余 `.content` 读取已都在基座。

**X-3【中】状态与契约用字符串表达，类型系统没起作用**（贯穿基座、书架、网关、前端）
- 书架：`sidecar.rs:30-45` 的 `DeliverCheck.status`/`RenderCheck.status` 是 `String`，`"pending"/"onopen"/"failed"/"timeout"` 字面量散落在 `library.rs:83,86,89,121,207`、`deliver.rs:88,183,193`、`render_check.rs:41,51`。
- 网关：`gateway/src/batch.rs:361-370,422` 按 `Value` 路径取 `delivered.<kind>.status` 再比字面量。
- 基座：文件夹"名字"与"uuid"都是 `&str`（`rmsvc-core/src/xochitl/mod.rs:87/93、108/114、131/136` 三对同签名入口）——这已造成过真实事故（note-serve 把 uuid 传给按名字的接口，09-09～10-09 笔记本落书库根，白皮书 §06 有记录）。
- 前端：同一批字面量在 `app.js` 再写一遍（见 FE-1）。

### 2.3 rmsvc-core 基座

**CORE-1【中】错误模型是"字符串 + 调用方猜状态码"，4xx/5xx 两个方向都会判错** ✔
- `http/mod.rs:266-270`：`impl From<String> for ApiError` 一律 500 → 领域校验错误（如 `fs.rs:61` "非法文件名"）直接 `?` 上来就成了 500。
- 反向：全仓库 33 处 `map_err(ApiError::bad)`，如 `enhance/wallpaper-serve/src/main.rs:122` 把含写盘 I/O 失败的 `activate` 报成 400。
- `read_small_body/json_body/form_body`（`mod.rs:152/173/185`）返回 `String`，拿不到 413；没有任意状态码构造器，调用方手写结构体字面量（`gateway/src/proxy.rs:42,67`、`book-serve/src/api.rs:214`）。
- GET 类跨服务调用丢状态码：`registry.rs:154-163` 的 `get_json/get_typed` 只返回 `String`，于是 mind-serve 一律当 404（`mind-serve/main.rs:72`），note-serve 一律当 400（`note-serve/main.rs:130/149/164/173`，连"ink-serve 未运行"也回 400）。POST 侧已有 `try_post_json → SvcError{status}`，GET 侧缺对称实现。

**CORE-2【中】`xochitl/library.rs` 内两套 `.metadata` 模型**
- 基于 `Value` 的 `str_of/is_live/created_ms`（`library.rs:34-52`）与强类型 `Metadata` 的同名方法（`188-203`）重复；`"CollectionType"/"DocumentType"` 字面量出现 7 次；`read_metadata`（Value）与 `read_meta`（强类型）并存，前者无外部调用。

**CORE-3【中】基座混入单服务领域模块，违背"不含书/笔记/字体业务语义"的自我定位**

**CORE-5【中，已知取舍】http ↔ events 循环依赖 + thread_local 隐式传参**
- `http/router.rs:139-140` 在每个请求里调用 `events::enter_request`；`events.rs:7` 反向引用 `http::Reply`；隐式状态 `REQUEST_KEEPALIVE`（`events.rs:30-35`）。当初理由是"不用改调用方"，现在代价只是 7 个 `/events` 路由各改一行。

## 三、优化优先级

排序依据：**风险 × 影响面 ÷ 改动成本**。凡改变设备行为的项，按项目纪律需真机验证后才算完成。

| 优先级 | 项目 | 理由 | 改动面 | 真机验证 |
|---|---|---|---|---|
| **P0** | SEC-1 rustls 升级 | 网络可利用的 DoS，无补丁版本 | vendored tiny_http `ssl/rustls.rs`（~120 行）+ vendor README | 必须（HTTPS 登录、长连接 SSE） |
| **P0** | SEC-2/SEC-3 CI 补漏 | 一次性投入，长期防回归；SEC-1 本应被 CI 抓到 | `ci.yml` 一个文件 | 否 |
| **P1** | X-1 统一投递 + 认领 + 文件夹解析 | 唯一的结构性耦合点，带认错书与落错文件夹两个行为风险 | rmsvc-core xochitl、book-serve 4 文件、note-serve publish | 必须 |
| **P1** | NT-1 + NT-2 条目状态机 + EntryPatch | 有可推演的真实 bug，且可能清空用户回答 | notecore model + ink/transcribe/mind 三处 | 必须（转写→补笔→再转写） |
| **P1** | FE-9、FE-3、SH-4 用户可见文案 | 成本极低（几行到 ~20 行测试），直接消除用户可见错误 | 少量 | FE-9/SH-4 网页目测即可 |
| **P2** | 前后端契约（FE-1/2/4/5/6 + GW-1/GW-2 + X-3） | 已出现过漂移 bug；按第四节方案渐进 | 跨服务，分批 | 网页功能回归 |
| **P2** | CORE-1 错误模型 | 状态码误判影响排障与前端提示 | 基座小、服务侧分批 | 否（host 测试足够） |
| **P2** | X-2 PageTable 下沉 | 格式知识应唯一 | 基座 1 类型 + 两服务各删 ~10 行 | 建议（阅读进度找回） |

建议推进顺序：P0 两项 → FE-9/FE-3/SH-4 顺手 → X-1（先改 SH 文件夹解析，最小且修行为，再抽 `XochitlDelivery`）→ NT-1+NT-2 → 契约第一批（S4+S3）→ 其余。

### 4.2 契约方案对比（适配"无构建工具链、二进制内嵌、设备端部署"）

| 方案 | 优势 | 劣势（风险） | 适配度 |
|---|---|---|---|
| S1 Rust 生成 JSON Schema / TS 声明（schemars、ts-rs、typeshare） | 字段与枚举都由机器保证 | 前端是纯 JS，真正用上需 JSDoc + `tsc --noEmit` → 引入 npm，破坏 CI 零依赖；网关不依赖 book-serve/notecore，生成物需跨 crate 汇总；多 proc-macro，aarch64 交叉编译变慢 | **低** |
| S2 Rust 为源、编译期注入常量（把 `__EXTS__` 扩展为 `__CONTRACT__`） | 复用现成机制，零请求零依赖；前端写 `C.deliver.OK` 代替字面量 | 只能注入网关看得见的常量，跨服务枚举需先下沉；只管"取值集合"不管"字段形状" | **中高** |
| S2′ 共享 `contract.json`，Rust `include_str!`、前端 fetch | 不用下沉 crate | 两份源仍需测试对齐；多一次异步请求，会重现语言包那类加载时序坑 | 中 |
| S3 手写 + 契约测试（golden fixture、动态 i18n 键测试） | 零新依赖、可渐进；能抓字段形状漂移 | 只覆盖测到的路径，fixture 需维护 | **高** |

具体落点：
1. **S4**：`StagingEntry` 加 `title`（由 `canonical_book_name` 算，解 FE-2）和 `done`（解 FE-1 加入状态镜像）；`Entry` 加只读的 `view: browse|organize|trash`（解 `app.js:852` 镜像）；`/api/enhance/status` 返回 `toggles:[{key,on,loaded}]`（解 GW-2，前端不再认识 `.so/.qmd` 文件名）。
2. **S3**：Rust 侧加一个测试遍历 OTA 原因码、批量动作、WiFi 状态、agent 失败种类，断言两份语言包都有对应键（约 20 行，解 FE-3）；为 `/staging/list`、`/entries` 等关键接口落 golden fixture，node 测试与 puppeteer 冒烟共用（当前冒烟里的手写 mock 是同一契约的第三份拷贝）。
3. **S2**：在 rmsvc-core 新增仅依赖 serde 的 `wire` 模块（或独立小 crate，仿 `epubpkg`），放 `DeliverStatus/RenderStatus/EventKind` 等跨服务枚举；网关 `ui.rs` 把它们注入为 `__CONTRACT__`。
4. **前端源文件拆分（FE-8）**：

   | 方案 | 做法 | 优势 | 劣势 | 适配度 |
   |---|---|---|---|---|
   | M1 编译期拼接 | 拆为 `core.js/transfer.js/notes.js/manage.js/health.js/boot.js`，`ui.rs` 用 `concat!(include_str!(…))` 拼进同一 `<script>` | 运行时页面完全不变（单页、零额外请求）；无副作用的文件可被测试整文件加载 | 靠全局名字，无真正 import 隔离；拼接顺序须固定 | **高** |

   建议先做 M1，文件按 M2 标准写（只定义不执行，`boot.js` 例外），将来需要时可无痛升级。

## 五、建议采用的设计模式（对症表）

| 问题 | 模式 / 手法 | 落地形态 | 备注 |
|---|---|---|---|
| X-1 投递散落 | **Facade + Strategy** | `XochitlDelivery` 服务（建文件夹 → 上传/大文件通道 → 认领 → 登记页边距），认领判据为 `Matcher` 策略（字节相同 / 书名相符 / 大小相等）；基座提供 `Xochitl::upload_and_claim(body, folder, matcher, timeout)` | 跨进程交错用 `runtime_dir` 下锁文件 `flock` 替换进程内 `static Mutex` |
| X-1 任务模型两套 | **Command + 串行作业队列** | 落库与直接导入统一交给 `ImportJobs` 式串行队列；xochitl 上传本已被锁串行化，串行无吞吐损失 | 结果写回边车，api.rs 只取参/回执 |
| X-3 文件夹名 vs uuid | **Newtype / 和类型** | `FolderId(String)` 或 `enum Folder<'a>{Root, Named(&str), Id(FolderId)}`，三对入口合并为三个方法 | 让编译器兜住 09-09 那类事故 |
| X-3 / SH 字符串状态 | **类型化枚举（serde lowercase）** | `enum DeliverStatus`、`enum RenderStatus`，`#[serde(rename_all="lowercase")]` 保持线上格式 | 旧 `warn` 记录用一个变体兜住 |
| NT-1 条目状态 | **显式状态机（转移方法集中于聚合根）** | `Entry::accept_draft / revoke / revive`，transcribe 只发原文，ink-serve 只调方法 | DDD 意义上的聚合根；磁盘格式不变 |
| NT-2 改字端点 | **DTO + 命令端点** | `notecore::api::EntryPatch`、`BookBrief` 收发共用，解析失败回 400；可拆 `POST …/draft`、`…/answer` | 同时获得字段级权限 |
| CORE-1 错误 | **错误分类枚举（Error Kind）** | `ApiError::new/conflict/bad_gateway/too_large`；领域错误 `Invalid/NotFound/Conflict/Io`；`try_get_typed → SvcError` + `From<SvcError> for ApiError` | book-serve `ImportError` 是现成样板 |
| CORE-4 Reply | **代数数据类型** | `enum Body{Bytes, Sized{reader,len}, EventStream(reader)}` | 消除非法组合 |
| CORE-5 thread_local | **显式参数传递** | `sse_reply(&self, req)` 读 `req.q("ka")` | 删掉 router 钩子与循环依赖 |
| CORE-6 AssetStore | **接口隔离（ISP）** | 拆出 `UploadTarget` trait，`list/remove` 改为固有方法 | 3 个 impl |

| CORE-9 Request 构造 | **Builder** | `Request::test(method,path,body).query(..).header(..)` | 解除"不加字段"纪律的根因 |
| SH-1 代理队列 | **泛型模板方法** | `Handout<K: Hash+Eq+Clone>` + `AgentQueue<T: AgentItem>` | 约删 40 行 |
| GW-2 开关表 / PK-3 扩展登记 | **表驱动（Registry）** | Rust `const TOGGLES:&[Toggle{key,default,artifact}]`；shell `XOVI_EXTS` 表 | PK-3 等第三个扩展再做，避免过度设计 |

| FE-7 前端时序 | **显式状态机 + 对象封装** | `refreshGate`（state + why 记录）、`liveStream({onEvent,onReopen})` | 不改 coalesce/分档重取机制本身 |

**明确不建议的模式**：
- 不为 AI 厂商引入 trait 层级（已有 `Vision/TextModel` + `ChatClient` 的 Strategy 足够，厂商差异只在配置）。
- 不合并 notes 三个服务各自的窄 `EntryStore`/`Uploader`/`TrashSink` 接口（符合 ISP，是离线测试的接缝）。
- 不用 `#[serde(flatten)]` 合并 vendorcfg 配置公共字段——会改变键序，破坏"设备文件逐字节不变"的承诺；第三个 AI 服务出现前维持现状。
- 不采用 S1 代码生成路线（理由见 4.2）。

## 六、做得好、不应改动的部分

1. **服务边界**：各服务只读写自己的 `app_*_dir`，跨服务一律 `SvcClient`；网关 `MODULES` 唯一事实源 + 代理零业务知识（`gateway/src/proxy.rs:421-474`）。
2. **基座原语**：`fswatch::wait_for` 的"先挂监听再查"、`fs` 原子写/`ScratchFile` RAII/`move_into` 跨分区、`StampCache`（带 inode）与 `TtlCache` 各自的取舍、http 服务器 `Permit` 并发名额与 panic 兜底——都是真机教训打磨出来的。
3. **资源守卫**：`OpRegistry::try_guard → OpGuard`、`Kind::Replace{_busy}`、`PendingQueue<T> + Handout`、边车 Repository（`sidecar.rs` 的 `file_name_for` 唯一来源）。
4. **AI 后端 Strategy**：`Vision/TextModel` trait + `ChatClient` + `ClientCache`，编排逻辑全可用内存桩测试；`ChapterStore<T>/ConfigCell<C>/Ledger<Extra>` 只抽行为、磁盘格式不变。
5. **打包部署**：安装/卸载共用 `STEP_ORDER` 与 `manifest.sh` 单一清单、所有远程执行都经 `lib.sh` 封装；`xovi-ext-install.sh` 的"待换入区 + 待生效标记 + 整机重启生效"状态机是多次事故换来的，**不要改成看似更简洁的 restart 方案**。
6. **C 扩展 fail-safe**：`_xovi_shouldLoad` 按自身目标特征码判兼容、`_xovi_construct` 二次扫描、`--wrap=mmap` 复现分配失败路径的单测。
