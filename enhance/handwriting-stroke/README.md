# handwriting-stroke —— CJK 手写笔迹渲染优化（研究阶段，零实现代码）

**这里没有任何代码**，只是研究现状记录。别指望这个目录能编译/部署——真要有实现代码了再补 `src/`。

## 要做的是什么

设备手写笔锋按中文书写习惯（运笔粗细/顿挫）做渲染优化。**跟 `cardhw`（笔迹→文字的 AI 视觉识别，见 `knowledge/pkm-semantic/handwriting/`）完全无关**——那条线是"认出你写的字"，这条线是"你写字这个动作本身，笔画画出来好不好看"。用户 2026-09-09 明确澄清过这个区分（第一轮理解错了，以为是 `cardhw`）。

### ⚠️ 2026-09-09 晚间勘误：`FUN_00f401f0` 之前的分析是错的

在给出实现计划前照项目纪律做"反编译交叉核实原始汇编"，发现之前记的这段**不对，必须纠正，不能留着误导后续工作**：

之前记的（错）：
```c
float FUN_00f401f0(float param_1, long param_2)
{
  return param_1 * *(float *)(param_2 + 8);
}
```

原始汇编（真实情况）：
```asm
bti c
fmul s2,s2,s1              ; 入参不止 1 个 float，是 s0/s1/s2 三个
mov x1,#0x0
ldp s3,s1,[x0, #0x8]       ; s3=[x0+8], s1=[x0+0xc]——两个配置字段，不是只有一个
fmul s0,s0,s3              ; s0(入参) × [x0+8]
fmov w2,s0                 ; 结果A → w2
fmul s0,s2,s1              ; (s2×s1原始值) × [x0+0xc]
fmov w0,s0                 ; 结果B → w0
...(bfxil/bfm/lsr 把 w0/w2 拼进 s0:s1 寄存器对返回，ARM64 标准"返回一个2-float结构体"约定)
ret
```

真实签名是**3 个 float 入参 + 1 个对象指针，产出一对 `{float,float}`**——跟类名 `Varying2D` 对上（本来就该出两个值），不是"1 个 float 进、1 个 float 出、一行线性缩放"。反编译器把这个函数简化错了，之前只信了反编译 C 代码没有交叉核实原始汇编，是疏漏。

**更关键的问题**：`FUN_00f401f0` 在整个二进制里**从没有被真实调用点引用过**（`getReferencesTo` 只有 eh_frame 记账条目，零真实调用者）；`FUN_00f3f9d0` 里"算宽度"那段代码看起来是**内联计算**，不是在调 `FUN_00f401f0`。**这个函数是否真的会被真机执行到，静态反编译从来没有坐实过**——之前"最终结论"把"这个函数存在、挂在正确的 vtable 上"和"这个函数就是运行时真正被调用的那个"混为一谈了，这个断言过度自信，撤回。

`FUN_00f3f9d0` 这个真正逐点分派渲染的函数依然成立、依然是研究的主体，下面的分析原样保留，但**"想改宽度直接改 `FUN_00f401f0`"这条建议作废**——改动点得回到确认了真会执行到的 `FUN_00f3f9d0` 内联公式，或者先做真机验证确认 `FUN_00f401f0` 到底会不会被调用。

### 宽度插值本体：`FUN_00f3f9d0` 内联计算（确认会执行，`FUN_00f401f0` 是否被调用未坐实）

**以下分析基于 `FUN_00f3f9d0` 反编译——这个函数是从 `updateImage`（`FUN_008bbb80`）真实调用链上找到的，会执行到没有疑问；`FUN_00f401f0` 只是同一个 vtable 家族里的另一个方法，跟这里的内联公式关系待确认**：按笔型标签字节（`bVar16`，`*(byte*)(lVar7+0x70)`，值 3/`<4`/5/6/其它）分派到不同分支，每个分支各自算一遍宽度再调用不同的绘制原语。**最丰富的一支**（对应某个方向敏感的笔型，`bVar16` 落在非 3/5/6/`<4` 的那一档）：

```c
// 1) smoothstep 三次缓动曲线——目前发现的唯一非线性宽度处理
fVar11 = NEON_ucvtf(点结构offset0x8字段) * 0.25;
fVar15 = 1.0;
if (2.0 <= fVar11) {
  fVar15 = (10.0 < fVar11) ? 0.8 :
    (1.0 - (3.0 - t*2.0)*t*t) * 0.2 + 0.8,  // t = (fVar11-2.0)*0.125，标准 smoothstep 公式
}
// 2) 方向角 → sin/cos，只有某标志位打开才算（各向异性笔刷特征）
if (标志位 & 1) {
  方向角 = NEON_ucvtf(点结构offset0xC字段);
  sincosf(方向角 × 2π/255, &sin值, &cos值);   // 存进笔画状态，供绘制用
}
// 3) 最终宽度：跟简单分支同一套公式（基础偏移 ± 缩放系数×原始宽度字段），
//    smoothstep 曲线值(fVar15)存的位置(plVar6+0xe)没有再参与这次宽度计算，
//    用途待确认（可能是给填充透明度/羽化半径用，不是宽度本身）
最终宽度 = fVar13(基础偏移 0.75或0.0) + 缩放系数 × NEON_ucvtf(点结构offset0xA字段)×0.25;
FUN_00f47530((float)当前点x, (float)当前点y, lVar7);   // 用这个宽度值做几何
```

再往下，**`FUN_00f47530` 是变宽笔画的几何生成器**：拿"上一点半宽 + 当前点半宽 + 两点连线的垂直方向单位向量"，算出一个梯形的四个角点（两端分别沿垂直方向偏移各自的半宽）。**变宽笔画的几何能力天然存在**（两端半宽独立，不要求相等），缺的是"宽度该怎么按 CJK 书写习惯算"这一环。

梯形算出来之后交给 `FUN_00f37d30`，往下是**四级级联的 Sutherland-Hodgman 多边形裁剪**（`FUN_00f37d30 → FUN_00f378e0 → FUN_00f376b0 → FUN_00f374f0`）：逐条边跟脏矩形/裁剪区做交点线性插值，把梯形切成落在裁剪区内的三角形，纯几何、不碰颜色，全程固定代码（非虚函数）。裁剪链**最后一级不再调下一个裁剪函数，改成虚函数间接调用**：

```c
(**(code **)(*(long *)*param_1 + 0x10))((long *)*param_1, &裁剪后的三角形坐标, 0, 0);
```

`vtable+0x10` 跟全程反复见到的槽位模式一致（`VaryingGenerator_WidthLength::generate()`/`Fill*` 分派都是这个偏移）——**到此为止，几何裁剪交棒给多态的像素消费者（`CoverageBuffer`/`Fill*`，具体是哪个实例取决于当前笔型选中了哪个组合成员）**，静态反编译单函数看不出运行时 `*param_1` 到底指向谁，这是这条链目前能挖到的边界，往下需要动态分析或更细致的字段级数据流追踪。

**完整链路（五层，全部走完）**：

```
①.rm 点结构（x/y/宽度×2/方向角/压感）
  ↓
②FUN_00f3f9d0 按笔型标签分派算宽度
    → 简单笔型：宽度 = 基础偏移 ± 缩放系数×原始宽度字段（纯线性）
    → 方向敏感笔型：+ smoothstep 缓动曲线（唯一非线性处，用途未完全确认）
                   + 方向角→sin/cos（各向异性笔刷特征，笔锋朝向参与渲染）
  ↓
③FUN_00f47530：拿两点各自半宽 + 连线方向，构造变宽梯形几何
  ↓
④FUN_00f37d30→FUN_00f378e0→FUN_00f376b0→FUN_00f374f0：四级多边形裁剪（固定代码）
  ↓
⑤虚函数间接调用（`vtable+0x10`）→ 多态像素消费者（CoverageBuffer/Fill*，运行时决定）
```

**架构结论**：整条"笔画变像素"的链路是"固定几何算法（宽度插值+变宽四边形+多边形裁剪，全部非虚函数）+ 最后一步虚函数分发给可插拔的像素填充策略"——跟 `StrokeRenderer` 构造函数"组合十几个多态成员、按需切换"的整体设计首尾呼应。

**对"CJK 手写按书写习惯优化"这个诉求，从浅到深三个可改层次**（都落在②这一层，③④⑤是通用几何/分发管线，跟笔型无关，不需要动）：
1. 改 `FUN_00f3f9d0` 内联公式的线性缩放系数——只能整体调粗细比例，没有顿挫感（`FUN_00f401f0` 是否真的参与渲染未坐实，见上面勘误，先别当成改动目标）。
2. 改 smoothstep 曲线参数（阈值 `2.0`/`10.0`、输出范围 `0.8~1.0`）——能调"越宽边缘越怎样"，曲线形状固定，调不出运笔快慢的动态感。
3. **在宽度计算里注入笔画方向相关的权重**（读点结构 offset `0xC` 方向角字节，仿照已有的方向敏感分支做法，但这次调宽度不是纹理朝向）——目前所有分支的宽度公式都只跟"距离/压感/固定曲线"相关，没有"横竖撇捺方向不同粗细"这层，这是最贴近"CJK 书写习惯"诉求、但也没有现成代码可抄的一层，需要新写逻辑，不是改现有参数就能达到。

### 14 字节点结构（`FUN_00f36be0` 反解，独立验证过）

| 偏移 | 类型 | 换算 | 字段 |
|---|---|---|---|
| `0x0` | float | 原样 | x 坐标 |
| `0x4` | float | 原样 | y 坐标 |
| `0x8` | u16 | `×0.25` | 宽度/速度（16 位定点，待进一步区分具体是哪个） |
| `0xA` | u16 | `×0.25` | 另一个同类字段 |
| `0xC` | u8 | `×2π/255` | 方向角（0-255 → 0~2π） |
| `0xD` | u8 | `÷255` | 压感（0-255 → 0~1，归一化） |

## 上一轮判断被推翻的地方（如实记录，别再犯）

第二轮（脚本反查 vtable 失败）曾经下结论"这几个 `Fill*` 类可能没有虚函数表"——**这个结论是错的**。这些类（`CoverageBuffer`/`VaryingGenerator_*` 等）确实有 vtable，只是它们是 `StrokeRenderer` 的**内联组合成员**（不是独立 `new` 出来的堆对象），vtable 指针是构造函数里按值直接塞进对象内存，没有任何地方存一个"指向这个成员 typeinfo 的裸指针"——这正是第二轮"反查谁指向 typeinfo"这条路天生走不通的原因，不是这些类没有虚函数。找到正确路径靠反过来走：QML 类型注册 → 构造函数工厂 → 构造函数体里的 vtable 安装序列 → 用 Ghidra `Search → Memory` 裸字节搜 typeinfo 地址，才在构造函数自己的字段里找到命中。

## 排查方法论（下次直接抄，别重新摸索）

1. **调试/异常字符串是金矿**：这次能挂上名字的每一步（`ShapesOverlay`/`saveStroke`/`updateImage`/`"New StrokeRenderer,"`/`shapesoverlay.cpp` 源码路径）都是从 Qt 编译进二进制的错误提示文案挖出来的，不是靠符号表（xochitl 符号被剥干净了，函数名全是 `FUN_xxxxx`，Symbol Tree → Functions 按名字搜是空的）。以后先扫这类字符串再决定往哪个函数深挖，效率比瞎猜地址高得多。
2. **多态类找 vtable 走"构造函数正向安装"，别走"typeinfo 反向反查"**：`ShapesOverlay` 这种独立堆对象/QML 注册类型，走"QML 工厂函数 → 构造函数开头 `str [x0]` 存 vtable 指针"最快；`StrokeRenderer` 内部那些内联组合成员，走"构造函数体里挨个 `param_1[N] = &PTR_FUN_xxx` 赋值"最快——两种都不需要反查 typeinfo。
3. **实在要反查裸指针，Ghidra `Show References To` 不够用就上 `Search → Memory`（按十六进制字节序列搜）**——前者依赖分析器已经把某处识别成指针类型，后者是纯字节扫描，跟本项目 `cj_find_metaobject` 手法等价，但 GUI 里能立刻看到命中上下文。
4. **Java Swing 在 Wayland（尤其平铺式合成器）下经典症状是整个窗口空白、菜单栏画不出来**——环境变量 `_JAVA_AWT_WM_NONREPARENTING=1` 能修，遇到"Ghidra 打开是白屏"先试这个，不用怀疑工程文件损坏。
5. **一旦有了具体地址，headless 脚本能接手，不用继续劳烦人工 GUI 截图**：GUI 阶段是"探索式的——不知道该往哪查"时才必须靠人工交互；一旦定位到具体函数地址，反编译指定函数、查某地址的 xref、按字节序列搜内存，这些操作 Ghidra headless 脚本 API 全都能做（`DecompInterface`/`getReferencesTo`/直接读内存字节），跟 GUI 里手动点是等价操作。`FUN_00f3f9d0`→`FUN_00f47530` 这一段完整链路就是这样自主挖出来的，全程没再要求截图。**前提是 GUI 工程处于关闭状态**（headless 和 GUI 不能同时开同一个工程，会抢 `.lock`）。

## 下一步（没做，真要做需要真机验证）

1. **像素消费者（`vtable+0x10` 那个虚函数调用的真实目标）没有确认**——裁剪链五级全走完了，最后一步是虚函数分发，静态反编译单函数看不出运行时 `*param_1` 指向哪个具体的 `CoverageBuffer`/`Fill*` 实例。要精确到"这个笔型最终调的是哪个类的哪个方法"需要动态分析（真机 hook 打日志观察，或者更细致地把 `StrokeRenderer` 每个字段的赋值来源都过一遍）。**对"运笔粗细/顿挫"这个诉求不需要这层**——③④两层是通用几何/裁剪管线，跟笔型无关，改动点全在②。
2. **smoothstep 缓动曲线（`fVar15`，存进 `plVar6+0xe`）的下游用途没有确认**——猜测是喂给填充透明度/羽化半径，没有跟踪到读它的地方，如果要精确复刻"越宽边缘越怎样"的观感需要先确认这个。
3. **`bVar16`（笔型标签字节）每个取值具体对应哪个 `Fill*`/`VaryingGenerator_*` 类没有交叉验证**——只是从"方向敏感 vs 不敏感"推断出大致分组，没有对着 `StrokeRenderer` 构造函数里那十几个组合成员的偏移逐一核对过。
4. **判断有没有稳定可 hook 的点**：三个可改层次（简单缩放/缓动曲线参数/新增方向权重）里，第三层需要新写逻辑不是改参数，风险和工作量都高得多；前两层改动点小、物理上容易 hook，但要先确认路径触发条件（是不是每次画笔迹都走到、会不会被别的调用方依赖）。参照 `enhance/hl-snap/src/hl_snap.c` 现有 hook 的判据标准（特征码定位、fail-safe 开关）。
5. **真有 hook 点了，这个目录才升级成有 `src/` 的实现**——大概率也会照 `hl-snap/` 的样子做成独立最小 xovi 扩展，不塞进别的项目。**改设备渲染路径风险级别高，动手前必须先只读验证（打日志确认真实取值），不能直接写内存**，按项目工程纪律"先离线摸清楚再写"执行。目前这轮排查全程零代码零真机验证，纯静态反编译。
