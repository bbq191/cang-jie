# handwriting-stroke —— CJK 手写笔迹渲染优化

**两个 hook 目标已经真机部署验证**（2026-09-10，`FUN_00f47530`〔书法笔专属〕+`FUN_00f4c8d0`〔钢笔/铅笔/马克笔等日常工具，覆盖面是前者近 5 倍〕，笔尖角度模型+提按速度代理两个效果，见「实现」一节）——研究阶段的完整反解过程见下面，代码在 `src/hw_stroke.c`，构建/部署仿 `enhance/hl-snap/`（host 侧一键：`packaging/deploy-handwriting-stroke.sh <host>`，2026-09-11 新增）。**最常用的钢笔/铅笔量级工具（`bVar16<4`）仍然摸不到**，是当前最大的缺口，见「下一步」。

## 要做的是什么

设备手写笔锋按中文书写习惯（运笔粗细/顿挫）做渲染优化。**跟 `cardhw`（笔迹→文字的 AI 视觉识别，见 `knowledge/pkm-semantic/handwriting/`）完全无关**——那条线是"认出你写的字"，这条线是"你写字这个动作本身，笔画画出来好不好看"。用户 2026-09-09 明确澄清过这个区分（第一轮理解错了，以为是 `cardhw`）。

### ⚠️ 2026-09-09 晚间勘误：`FUN_00f401f0` 之前的分析是错的

在给出实现计划前照项目纪律做"反编译交叉核实原始汇编"，发现之前记的这段**不对，必须纠正，不能留着误导后续工作**：

之前记的（错）：
```c
float FUN_00f401f0(float param_1, long param_2)
{
  return param_1 * *(float *)(param_2 + 8);
}
```

原始汇编（真实情况）：
```asm
bti c
fmul s2,s2,s1              ; 入参不止 1 个 float，是 s0/s1/s2 三个
mov x1,#0x0
ldp s3,s1,[x0, #0x8]       ; s3=[x0+8], s1=[x0+0xc]——两个配置字段，不是只有一个
fmul s0,s0,s3              ; s0(入参) × [x0+8]
fmov w2,s0                 ; 结果A → w2
fmul s0,s2,s1              ; (s2×s1原始值) × [x0+0xc]
fmov w0,s0                 ; 结果B → w0
...(bfxil/bfm/lsr 把 w0/w2 拼进 s0:s1 寄存器对返回，ARM64 标准"返回一个2-float结构体"约定)
ret
```

真实签名是**3 个 float 入参 + 1 个对象指针，产出一对 `{float,float}`**——跟类名 `Varying2D` 对上（本来就该出两个值），不是"1 个 float 进、1 个 float 出、一行线性缩放"。反编译器把这个函数简化错了，之前只信了反编译 C 代码没有交叉核实原始汇编，是疏漏。

**更关键的问题**：`FUN_00f401f0` 在整个二进制里**从没有被真实调用点引用过**（`getReferencesTo` 只有 eh_frame 记账条目，零真实调用者）；`FUN_00f3f9d0` 里"算宽度"那段代码看起来是**内联计算**，不是在调 `FUN_00f401f0`。**这个函数是否真的会被真机执行到，静态反编译从来没有坐实过**——之前"最终结论"把"这个函数存在、挂在正确的 vtable 上"和"这个函数就是运行时真正被调用的那个"混为一谈了，这个断言过度自信，撤回。

`FUN_00f3f9d0` 这个真正逐点分派渲染的函数依然成立、依然是研究的主体，下面的分析原样保留，但**"想改宽度直接改 `FUN_00f401f0`"这条建议作废**——改动点得回到确认了真会执行到的 `FUN_00f3f9d0` 内联公式，或者先做真机验证确认 `FUN_00f401f0` 到底会不会被调用。

### 宽度插值本体：`FUN_00f3f9d0` 内联计算（确认会执行，`FUN_00f401f0` 是否被调用未坐实）

**以下分析基于 `FUN_00f3f9d0` 反编译——这个函数是从 `updateImage`（`FUN_008bbb80`）真实调用链上找到的，会执行到没有疑问；`FUN_00f401f0` 只是同一个 vtable 家族里的另一个方法，跟这里的内联公式关系待确认**：按笔型标签字节（`bVar16`，`*(byte*)(lVar7+0x70)`，值 3/`<4`/5/6/其它）分派到不同分支，每个分支各自算一遍宽度再调用不同的绘制原语。**最丰富的一支**（对应某个方向敏感的笔型，`bVar16` 落在非 3/5/6/`<4` 的那一档）：

```c
// 1) smoothstep 三次缓动曲线——目前发现的唯一非线性宽度处理
fVar11 = NEON_ucvtf(点结构offset0x8字段) * 0.25;
fVar15 = 1.0;
if (2.0 <= fVar11) {
  fVar15 = (10.0 < fVar11) ? 0.8 :
    (1.0 - (3.0 - t*2.0)*t*t) * 0.2 + 0.8,  // t = (fVar11-2.0)*0.125，标准 smoothstep 公式
}
// 2) 方向角 → sin/cos，只有某标志位打开才算（各向异性笔刷特征）
if (标志位 & 1) {
  方向角 = NEON_ucvtf(点结构offset0xC字段);
  sincosf(方向角 × 2π/255, &sin值, &cos值);   // 存进笔画状态，供绘制用
}
// 3) 最终宽度：跟简单分支同一套公式（基础偏移 ± 缩放系数×原始宽度字段），
//    smoothstep 曲线值(fVar15)存的位置(plVar6+0xe)没有再参与这次宽度计算，
//    用途待确认（可能是给填充透明度/羽化半径用，不是宽度本身）
最终宽度 = fVar13(基础偏移 0.75或0.0) + 缩放系数 × NEON_ucvtf(点结构offset0xA字段)×0.25;
FUN_00f47530((float)当前点x, (float)当前点y, lVar7);   // 用这个宽度值做几何
```

再往下，**`FUN_00f47530` 是变宽笔画的几何生成器**：拿"上一点半宽 + 当前点半宽 + 两点连线的垂直方向单位向量"，算出一个梯形的四个角点（两端分别沿垂直方向偏移各自的半宽）。**变宽笔画的几何能力天然存在**（两端半宽独立，不要求相等），缺的是"宽度该怎么按 CJK 书写习惯算"这一环。

梯形算出来之后交给 `FUN_00f37d30`，往下是**四级级联的 Sutherland-Hodgman 多边形裁剪**（`FUN_00f37d30 → FUN_00f378e0 → FUN_00f376b0 → FUN_00f374f0`）：逐条边跟脏矩形/裁剪区做交点线性插值，把梯形切成落在裁剪区内的三角形，纯几何、不碰颜色，全程固定代码（非虚函数）。裁剪链**最后一级不再调下一个裁剪函数，改成虚函数间接调用**：

```c
(**(code **)(*(long *)*param_1 + 0x10))((long *)*param_1, &裁剪后的三角形坐标, 0, 0);
```

`vtable+0x10` 跟全程反复见到的槽位模式一致（`VaryingGenerator_WidthLength::generate()`/`Fill*` 分派都是这个偏移）——**到此为止，几何裁剪交棒给多态的像素消费者（`CoverageBuffer`/`Fill*`，具体是哪个实例取决于当前笔型选中了哪个组合成员）**，静态反编译单函数看不出运行时 `*param_1` 到底指向谁，这是这条链目前能挖到的边界，往下需要动态分析或更细致的字段级数据流追踪。

**完整链路（五层，全部走完）**：

```
①.rm 点结构（x/y/宽度×2/方向角/压感）
  ↓
②FUN_00f3f9d0 按笔型标签分派算宽度
    → 简单笔型：宽度 = 基础偏移 ± 缩放系数×原始宽度字段（纯线性）
    → 方向敏感笔型：+ smoothstep 缓动曲线（唯一非线性处，用途未完全确认）
                   + 方向角→sin/cos（各向异性笔刷特征，笔锋朝向参与渲染）
  ↓
③FUN_00f47530：拿两点各自半宽 + 连线方向，构造变宽梯形几何
  ↓
④FUN_00f37d30→FUN_00f378e0→FUN_00f376b0→FUN_00f374f0：四级多边形裁剪（固定代码）
  ↓
⑤虚函数间接调用（`vtable+0x10`）→ 多态像素消费者（CoverageBuffer/Fill*，运行时决定）
```

**架构结论**：整条"笔画变像素"的链路是"固定几何算法（宽度插值+变宽四边形+多边形裁剪，全部非虚函数）+ 最后一步虚函数分发给可插拔的像素填充策略"——跟 `StrokeRenderer` 构造函数"组合十几个多态成员、按需切换"的整体设计首尾呼应。

**对"CJK 手写按书写习惯优化"这个诉求，从浅到深三个可改层次**（都落在②这一层，③④⑤是通用几何/分发管线，跟笔型无关，不需要动）：
1. 改 `FUN_00f3f9d0` 内联公式的线性缩放系数——只能整体调粗细比例，没有顿挫感（`FUN_00f401f0` 是否真的参与渲染未坐实，见上面勘误，先别当成改动目标）。
2. 改 smoothstep 曲线参数（阈值 `2.0`/`10.0`、输出范围 `0.8~1.0`）——能调"越宽边缘越怎样"，曲线形状固定，调不出运笔快慢的动态感。
3. **在宽度计算里注入笔画方向相关的权重**（读点结构 offset `0xC` 方向角字节，仿照已有的方向敏感分支做法，但这次调宽度不是纹理朝向）——目前所有分支的宽度公式都只跟"距离/压感/固定曲线"相关，没有"横竖撇捺方向不同粗细"这层，这是最贴近"CJK 书写习惯"诉求、但也没有现成代码可抄的一层，需要新写逻辑，不是改现有参数就能达到。

## 上一轮判断被推翻的地方（如实记录，别再犯）

第二轮（脚本反查 vtable 失败）曾经下结论"这几个 `Fill*` 类可能没有虚函数表"——**这个结论是错的**。这些类（`CoverageBuffer`/`VaryingGenerator_*` 等）确实有 vtable，只是它们是 `StrokeRenderer` 的**内联组合成员**（不是独立 `new` 出来的堆对象），vtable 指针是构造函数里按值直接塞进对象内存，没有任何地方存一个"指向这个成员 typeinfo 的裸指针"——这正是第二轮"反查谁指向 typeinfo"这条路天生走不通的原因，不是这些类没有虚函数。找到正确路径靠反过来走：QML 类型注册 → 构造函数工厂 → 构造函数体里的 vtable 安装序列 → 用 Ghidra `Search → Memory` 裸字节搜 typeinfo 地址，才在构造函数自己的字段里找到命中。

## 排查方法论（下次直接抄，别重新摸索）

1. **调试/异常字符串是金矿**：这次能挂上名字的每一步（`ShapesOverlay`/`saveStroke`/`updateImage`/`"New StrokeRenderer,"`/`shapesoverlay.cpp` 源码路径）都是从 Qt 编译进二进制的错误提示文案挖出来的，不是靠符号表（xochitl 符号被剥干净了，函数名全是 `FUN_xxxxx`，Symbol Tree → Functions 按名字搜是空的）。以后先扫这类字符串再决定往哪个函数深挖，效率比瞎猜地址高得多。
2. **多态类找 vtable 走"构造函数正向安装"，别走"typeinfo 反向反查"**：`ShapesOverlay` 这种独立堆对象/QML 注册类型，走"QML 工厂函数 → 构造函数开头 `str [x0]` 存 vtable 指针"最快；`StrokeRenderer` 内部那些内联组合成员，走"构造函数体里挨个 `param_1[N] = &PTR_FUN_xxx` 赋值"最快——两种都不需要反查 typeinfo。
3. **实在要反查裸指针，Ghidra `Show References To` 不够用就上 `Search → Memory`（按十六进制字节序列搜）**——前者依赖分析器已经把某处识别成指针类型，后者是纯字节扫描，跟本项目 `cj_find_metaobject` 手法等价，但 GUI 里能立刻看到命中上下文。
4. **Java Swing 在 Wayland（尤其平铺式合成器）下经典症状是整个窗口空白、菜单栏画不出来**——环境变量 `_JAVA_AWT_WM_NONREPARENTING=1` 能修，遇到"Ghidra 打开是白屏"先试这个，不用怀疑工程文件损坏。
5. **一旦有了具体地址，headless 脚本能接手，不用继续劳烦人工 GUI 截图**：GUI 阶段是"探索式的——不知道该往哪查"时才必须靠人工交互；一旦定位到具体函数地址，反编译指定函数、查某地址的 xref、按字节序列搜内存，这些操作 Ghidra headless 脚本 API 全都能做（`DecompInterface`/`getReferencesTo`/直接读内存字节），跟 GUI 里手动点是等价操作。`FUN_00f3f9d0`→`FUN_00f47530` 这一段完整链路就是这样自主挖出来的，全程没再要求截图。**前提是 GUI 工程处于关闭状态**（headless 和 GUI 不能同时开同一个工程，会抢 `.lock`）。

## 实现（2026-09-10，真机部署验证，`src/hw_stroke.c`）

用户问"可以实现吗？落计划，仔细认真开发一版试试"——落地过程分好几轮，有成也有撤回，如实记，不是一路顺风：

### hook 目标：改用 `FUN_00f47530`，不用 `FUN_00f401f0`

计划阶段先纠正了一个前提：`FUN_00f401f0` 从没被真实调用点引用过（见上面「上一轮判断被推翻的地方」的姊妹问题），改用**确认在真实调用链上、签名简单可靠**的 `FUN_00f47530`（变宽梯形几何生成器）——两个 float（AAPCS64 走 s0/s1）+ 一个指针（走 x0），标准调用约定，函数入口第一件事就是读"当前点宽度"（`(char*)ctx+4`）算半宽，改这里最简单。

### Step 1/2：验证机制可行（真机截图确认）

先部署纯诊断 hook（只读 log，call-through 不改任何值）：真机手写笔连续打日志，`w` 数值合理且随笔压连续渐变（起笔轻→行笔重→收笔轻），证实抓对了数据流。再加一个从 `reading-qol.json` 读的浮点开关 `hwStrokeWidthFactor`（默认 1.0=不变），改成 2.5/0.5 真机截图肉眼确认笔画明显变粗/变细——**证实"改这条渲染路径能真实影响笔迹粗细"这件事本身可行**。

### 笔尖角度模型（社区调研落地）

用户反馈"CJK 顿挫不是单纯粗细问题"，调研西式书法笔工具的经典公式（Illustrator/Inkscape 的 Calligraphic Brush 同款）：

```
宽度 ×= min_ratio + (1-min_ratio) × |sin(运笔方向角 − 笔尖固定角度)|
```

运笔方向角**不依赖点结构的方向字节**（真机诊断过：日常"中粗钢笔"走 `bVar16<4` 纯线性分支，压根不会往方向字段那条路径走）——改成在 `FUN_00f47530` 自己内部维护的"上一个点坐标"（`ctx+0x48`/`ctx+0x4c`）现算方向，这段状态所有笔型都统一走到，不挑分支。**踩了两个 GLIBC 符号版本坑**：`atan2f`/`sqrtf` 都需要 `GLIBC_2.43`，交叉编译工具链链的新版 glibc，设备上的 `libm.so.6` 没这么新，`dlopen` 直接解析失败（**而且拖累了同一次扫描里的 `hl-snap` 也加载不了，收尾要检查连带影响**）——改用 `sin(a-b)=sin(a)cos(b)-cos(a)sin(b)` 三角恒等式展开绕开 `atan2f`（只用 `sinf`/`cosf`/`fabsf`，`GLIBC_2.17`）；`__builtin_sqrtf` + `-fno-math-errno` 编译选项让 GCC 把 `sqrtf` 内联成 ARM64 原生 `FSQRT` 指令，不再走 libm 符号。

### 效果强度按基础宽度自动挂钩（用户反馈驱动的调整）

真机测试反馈"钢笔上效果不好，paintbrush 上还行"——诊断发现两者走**同一条代码分支、同一套公式**，只是钢笔基础宽度细（1.5~7.5），同样比例的方向摆动在细笔画上显得突兀，在毛笔粗笔画上才像书法笔触该有的过渡。改成**效果强度跟基础宽度挂钩**：`w` 低于 `hwStrokeNibWidthLow` 效果趋近关闭，高于 `hwStrokeNibWidthHigh` 满强度，之间线性过渡——不挑笔型，纯粗细驱动，细笔画自动没有效果、粗笔画自动有。

### ⚠️ 撤回：按 `bVar16`（笔型标签）精确排除钢笔——数据可靠性问题

一度尝试更精确的方案：直接读点结构笔型标签字节（`*(byte*)(ctx+0x70)`），强制排除钢笔（`bVar16==1`），不管钢笔多粗都不加效果。**真机测大号 paintbrush 时数据自相矛盾而撤回**：550 条记录 `w` 精确到小数点完全相同（`67.6222`），`fillType` 却几乎随机散布在整个 0~255——`x`/`y` 确实自然变化（537 个不同坐标，像真实运笔），说明这批是真数据，但 `ctx+0x70` 读到的不是稳定的笔型标签。根因：`bVar16` 是 `FUN_00f3f9d0` 读自己的 `*param_1`（记作 `lVar7`）的字段；**钢笔走的 `bVar16<4` 分支用的是 `plVar6`（`*(long**)(lVar7+0x68)`，另一个指针）做虚函数调用**，从没验证过这条路径下 `FUN_00f47530` 最终收到的 `ctx` 就是同一个 `lVar7`——只有"方向敏感"那个分支明确 `FUN_00f47530(x,y,lVar7)`。**`ctx+4`/`ctx+0x48`/`ctx+0x4c`/`ctx+0x5a` 这几个字段安全**（`FUN_00f47530` 自己的代码直接读写它们，不管上游哪条路径调进来都可靠），**`ctx+0x70` 不安全**（是借用 `FUN_00f3f9d0` 对它自己 `lVar7` 的解读，身份没有跨函数验证过）。最终退回纯宽度渐变方案，稳定可靠。

### 中文毛笔"提按"预研（2026-09-10 第二天）：压感数据真实存在但接不上，改用运笔速度代理

用户问"有力度吗"——headless 反编译 `FUN_00f3f9d0` 全函数体核实过：点结构 offset `0xD` 硬件压感字节（14 字节点结构表）确实被读出来转成 0~1 浮点，但存的是 `plVar6+0x74`，不是我们 hook 收到的 `ctx`（`ctx=plVar6[1]`，另一个对象）——直接读 `ctx` 偏移会重蹈 `bVar16` 那次覆辙。改用**不依赖 `plVar6`/`ctx` 任何字段**的独立算法：当前点在原始点数组里的地址 = `param_2[3] + (param_2[4]*0xe - 0xe)`，这条算法在 `FUN_00f3f9d0` 所有分支里完全一样，直接从 `FUN_00f3f9d0` 自己的入参算出来，不是猜的。

真机验证压感数据本身：
1. **第一次测试**（轻触→使劲按）：550 条记录里只有一次"接触瞬态"平滑爬坡（12→255，约 65 个采样点），之后不管写多重全部饱和在 255——说明这个字节在正常书写力度范围内几乎立刻饱和，**物理上采不到"轻重"区分度**，不是数据可靠性问题，是硬件/软件层的饱和特性。
2. **专测轻重力度**：这次分布是真实、宽范围连续变化的（3~255 全覆盖）——证明压感字节本身没问题，问题出在下一步。
3. **接入 `FUN_00f47530` 失败**：尝试用"`FUN_00f3f9d0` 入口设全局变量→`FUN_00f47530` 内部读"的方式跨函数传值（单线程同步调用，理论上可靠），但真机数据显示 3449 个诊断样本里只有 2 个落在会调用 `FUN_00f47530` 的分支，而 `FUN_00f47530` 自己却触发了 686 次——**说明 `FUN_00f47530` 的调用大部分根本不经过我们锁定的这一份 `FUN_00f3f9d0`**（早前反编译 xref 就看到 `FUN_00f3f9d0` 有 6 个不同调用点，很可能实时预览笔迹和提交进笔记本走不同路径）。

**结论：真实硬件压感数据存在且非垃圾数据，但跨函数传值这条路目前找不到可靠机制，放弃**。改用完全在 `FUN_00f47530`/`FUN_00f4c8d0` 自己 hook 内部就能算的运笔速度代理（复用已有的"上一点坐标"缓存算距离）：

```
speed_ratio = 1 − clamp((len−len_low)/(len_high−len_low),0,1) × (1−effective_min_ratio)
```

`len` 小（慢/顿笔）→ 比例趋近 1.0（粗）；`len` 大（快/带过）→ 比例趋近 `effective_min_ratio`（细）。跟笔尖角度模型同一套"效果强度按基础宽度自动挂钩"逻辑，代码里 `cj_hw_compute_delta`/`cj_hw_width_scaled_min_ratio` 两个函数被两个效果共用，避免重复。真机验证过方向正确（`len` 越大 `speed_ratio` 越低，数据里能看到明确相关性），当前受限于宽度阈值校准（见下）。

### 第二个 hook 目标：`FUN_00f4c8d0`（大幅扩大真实覆盖面）

真机测试发现一个重要架构事实：`FUN_00f47530` 只有"书法笔"这一个工具会走到（钢笔/铅笔/马克笔全都走完全不同的代码分支），而且**书法笔自己原生就有方向敏感的宽度模拟**（真实平头笔尖 chisel nib 物理效果，竖线可以是横线的 2~4 倍粗，这是真实校准过的笔尖角度模型该有的样子，不是 bug——两个效果都关掉后问题依然存在，真机验证过是原生行为）。也就是说，在书法笔上叠加我们自己的笔尖角度效果是重复造轮子，而钢笔/铅笔/马克笔这些日常工具完全摸不到这个 hook，之前"钢笔效果不好"的反馈很可能是没生效、看到的是原生渲染。

`FUN_00f3f9d0` 里 `bVar16==3`/`5`/`6` 三个分支各自调另一个"变宽几何生成器"，headless 反编译核实真实签名后发现：
- **`FUN_00f4c8d0`**（`bVar16==6` 直接调用、`bVar16==5` 经 `FUN_00f4d190` 写完宽度后间接调用）：`(float x, float y, undefined2 *ctx)`，宽度在 `ctx+4`（`param_3+2` 是 undefined2 单位=2 字节，换算成字节正好是 4）——**跟 `FUN_00f47530` 完全同一个调用约定**，前 20 字节纯栈操作（`paciasp`/`sub sp`/`stp x29,x30`/`add x29,sp`/`stp x19,x20`），没有分支/PC 相对寻址，patch 安全，直接复用同一套效果计算代码。
- **`FUN_00f4f430`**（`bVar16==3`）：签名也是 `(x,y,ctx)`、宽度也在 `ctx+4`，但**前 20 字节第 3 条指令是条件分支**（`ldrb w1,[x0,#0x78]; cbz w1,0x00f4f730`）——PC 相对寻址的指令被 `memcpy` 进 call-through stub 后，分支目标地址会因为指令搬了位置而算错，属于项目纪律明确排除的不安全形状（跟当初筛选 `FUN_00f47530` 的标准一致：`没有分支、没有 PC 相对寻址`），**没有拿来当 hook 目标**，留作已知但暂不可用的候选。

部署 `FUN_00f4c8d0` hook（诊断优先，先保持效果关闭确认真机加载正常）后，真机数据：**命中 10033 次**（`FUN_00f47530` 只有 2117 次），宽度覆盖 `w=3~36`——真实触及了日常常用的多种笔，覆盖面比只有书法笔时宽了近 5 倍。按这批真实数据重新校准阈值（`hwStrokeNibWidthLow=5`/`High=20`，`hwStrokeSpeedLenLow=1`/`High=10`），两个效果开到中等强度（`min_ratio=0.6`，比早期版本温和）。真机截图+用户反馈"看上去还行"，日常写字场景没有观察到方向异常/失真问题。

## 下一步（没做，真要做需要更多真机验证/静态分析）

1. **`bVar16<4` 分支（最常用的钢笔/铅笔量级工具）仍然摸不到**——这个分支是虚函数动态分发（`(**(code**)(*plVar6+0x10))(x,y,width,plVar6,...)`，width 直接当第 3 个参数传，不是存进字段再调用），运行时多态目标是哪个具体函数没有确认，需要新一轮调查（比如扩展现有诊断 hook 去读 `*(void**)(*plVar6+0x10)` 打印函数地址，再拿地址去反编译确认签名，跟这次找 `FUN_00f4c8d0` 同一个方法论）。
2. **`FUN_00f4f430`（`bVar16==3`）找到了但因为前 20 字节有条件分支不能安全 patch**——要用需要更精细的 trampoline 技术（指令级搬移/重定位分支目标），或者往后跳过这条分支的边界找一个更靠后、依然安全的 patch 点，都是新工作量，没有捷径。
3. **像素消费者（`vtable+0x10` 那个虚函数调用的真实目标）没有确认**——跟第 1 条是同一类问题（虚函数动态分发，静态反编译到边界）。

5. **当前参数（角度 45°/宽度阈值 5~20/速度阈值 1~10/两个强度都是 0.6）是按这一轮真机数据校准的起点，没有精细打磨**——"看上去还行"到"效果好"之间还有调参空间，非阻塞性后续工作。
