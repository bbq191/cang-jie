## 二、第 0 章：定位、原则与基础

### 00｜定位与原则

2026-09-03 用户提出"全面重构，补齐短板增强优势"（KOReader、微信读书、多格式、字体与屏保上传即用）。之后微读线砍了（§03u）、"上传时手选目标"被母版库取代（§03r）、电脑端命令行砍了（第九部分）、只收 EPUB/PDF（§03s）、KOReader 卸了（09-29）、设备上不再优化书（§03bw）。四条硬原则（用户两轮驳回后定）至今有效，现行表述见主白皮书「开发与维护 → 工程原则」。已退役的设计模式：投递 Strategy / Pipeline（§03s，规则统一后没了调用方）、CLI 相关模式；资产上传 10-10 前叫 `AssetStore`（带 list/remove），现为 `UploadTarget`。

### 01｜架构决策

**选 B：网关 + loopback 服务 + 注册表**（弃 A 每服务独立对外端口、C 单二进制编译期插拔）。注册表放 `$XDG_RUNTIME_DIR`（重启即清）+ 读时按 `/proc/<pid>` 清陈旧条目；代理**剥掉服务段**，后端直连与经网关同一套路由；每请求一线程；请求体流式透传，带长度的下载或 >256KB 应答流式（§03ah，09-24）。`bookconv` 当年从旧 weread-device 抽成独立 crate，2026-10-07 随书架不再优化书删除（§03bw），同日稍后连 sheng-ren `bookconv` 的依赖也去掉（§03bx）。

### 02｜XDG 路径表

现行路径表在主白皮书「接口与配置参考 → 设备上的路径」。qmd 的 XHR 只能写绝对路径（缺省值展开 `/home/root/.local/share/shelf/fonts.json`）。

### 03｜systemd

现行说明在主白皮书「组成部分」与「开发与维护」。来由：`ExecStartPre=-/usr/bin/fc-cache`（tmpfs 字体索引真重启后丢）2026-09-24 起从网关挪到 font-serve 的单元；**不给 xochitl 加任何依赖**（改核心服务启动依赖曾导致变砖）。

### 00b｜现状总览（2026-09-10 版）

09-10 时的架构（网关 + 四服务 + 注册表 + 事件总线；三层三动作）至今成立。**教训**：现状总览只留一份，旧版压成指针，避免两份"现状"互相矛盾（10-10 重组后现状只在主白皮书）。

## 三、第 A 章：入库与母版库

### 03b｜Phase 1 统一投递（2026-09-03，已被 §03r 取代）

当时留下、至今有效的只有：spool 目录结构（`inbox/`、`.work/`、`failed/` 封顶 50MB 带 `.reason`）与 `book.json` 三个配置键（`xochitlHost`/`uploadTimeoutSecs`/`nativeUploadLimitMb`）。直投路（`POST /?target=`、Strategy/Pipeline）§03s 删除。`books/done/` 是这一时期的遗留目录，全仓已无代码读写。**教训**：架构模式服务于当时的规则，规则变了就整块删，别留着当"以后可能用"。

### 03r｜读书线重构：中间层（母版库）三层架构（2026-09-05，用户"逻辑很乱"提出改造）

- **问题**：一次背 3 维决策（读器×投递口×文件夹），"优化"与"落库"耦合。**方案**：入库 / 优化 / 落库三动作正交，中间夹**母版库**；所有源一律原样直传母版库；**落库 = 纯复制原字节**。（优化 10-07 删除后只剩入库与落库两个动作。）
- **真机端到端（09-05）**：上传→优化→投 xochitl→（当时）adopt 进 KOReader（同字节）→母版保留。
- **规则漏洞两处**：inbox 自动直投 → 改为原样落母版库；格式转换产物"已优化"徽章说谎 → 当时按 `level` 分层（随优化删除）。
- **落库记录**：边车 `.<书>.delivered`；`GET /staging` 带 `freeBytes`，<300MB 红字告警（10-09 起由后端给 `lowSpace`）。剩余空间早期解析 busybox `df -k`，设备名过长把数字换行 → 改 `statvfs(2)`。
- **被取代**："收任意格式""优化档位""投完清除""电脑 shelf push""微读占位""清理已落库按钮"。
- **旧 PDF 重排教训（host 管线已砍）**：真机《财新周刊》整页空白的三根因＝每页一章、段落碎成行、图近整屏高；**先解剖产物再改**。

### 03s｜代码质量核查二轮：母版库领域化 · 直投路删除 · 上传模板统一（2026-09-05）

按"单一事实源 + 模板方法 + 门面"收：`rmsvc-core` 收 `formats`/`fs::plain_name`/`unique_path`/`http::bind`/上传模板；book-serve 删 `target.rs`/`pipeline.rs`，母版库拆成 `staging/` 下的领域文件。真机通（jpg 拒收、adopt 同字节、旧路由 404/405）。当时的"格式三档"（原生/电脑可转/仅 KOReader）09-17/18 收成一档。**教训**：格式收紧是用户策略，"KOReader 技术上能读"不构成收的理由。

### 03u｜砍微读线（2026-09-05，用户"不做了，直接砍微读线"）

微信读书官方网关只读没正文；正文要 web cookie（约 90 分钟过期）+ AGPL 派生解码；投入约两天、依赖第三方私有协议，用户决定不做。`weread-serve` 槽位、入库页占位都已删。**教训**：协议脆弱是常量。

### 03ap｜「抓网文」补「同步优化」复选框（2026-09-10；抓网文 2026-10-07 删除）

网文在 xochitl 上大片留空，一部分原因是抓取只走核心遍、不注入外链 css，于是加了"抓完紧接着优化"的复选框；但"图片夹正文"造成的留白**没有实质改善**（真因是分页引擎，§03aq）。**教训**：修了一个真实缺口，不等于解决了用户的问题。网页链接现在用 sheng-ren 收书。

### 03br｜入库 PDF 的「优化」：有文字层按原格式转 EPUB / 无文字层只裁边（2026-09-19 起，09-23 重做；2026-10-07 删除）

随书架不再优化书整个删除（§03bw）：`pdf_ingest`、本地 fork `pdf-extract-cj`、pdfwrite / pdfimg / pdf_epub、原 PDF 7 天备份与恢复接口都没了；第三方 PDF 现在原样加入 xochitl。

**当时的做法**：有文字层（每页平均可提取字符 ≥ 40）→ 按原格式转 EPUB（用户 09-23 拍板"按原格式（颜色，连接，图片位置）生成"）；漫画 / 扫描件 → 只裁白边、仍是 PDF；判不准一律只裁边。转成功后原 PDF 挪进 `staging/.pdf-originals/` 留 7 天、网页可恢复（**旧设备上这个目录里剩下的文件不再自动清**）。关键取舍：fork `pdf-extract` 只补颜色算子、图片位置、CID 字宽；颜色只用外链 class；图片按**视觉坐标**落位；有跨章跳转就合成单文件；每页只进一章。真机排查链：Word 导出的 8 页手册、calibre 导出的 540 页 T.E. 双语（T.E. 只渲染 1 页的根因是 OPF 非法 XML），两本当时都在真机上修好（排查链示意图已删除，见 git 历史）。09-24 第三轮审计给嵌套表单补了限深（`catch_unwind` 接不住栈溢出）。

**仍可迁移的教训**：① 核对跳转要分两套——目录看 `.epubindex`，正文链接看预览 PDF 的具名目标表。② 先用真书量化（字符数、图片引用数、链接数）再改代码。③ 破坏性的格式转换默认要留回头路。

## 七、第 E 章：稳定性、内存与耗电

> `systemd` 的 `MemoryMax` 在设备上实测不生效，内存全靠代码约束。2026-10-07 书架不再优化书后，下面几次内存事故的根源（设备上解码、重编码整本书的图片）整类消失；这里留"事故 → 根因 → 修法 → 教训"。定阈值铁律至今有效：**先实测 VmHWM，不靠"字节数乘法"估算**。（"内存防线"历史图已删除，见 git 历史。）

### 03ab｜代码结构重构记录（含 §03p · §03ag · §03ai；09-04 / 09-06 / 09-09）

共同原则：**只抽行为/传输样板，不合并各服务的业务语义和领域校验**。09-04（§03p）抽 `config`（首启写缺省、损坏不覆盖、原子保存）、`fs::write_atomic`；09-06 `clock`、边车读写拆成 `sidecar.rs`、网关 UI 拆成真文件；09-09（§03ag）`PendingQueue<T>`（持久化 + 入队去重 + 剔除），09-25 再抽长轮询 `Handout`、10-10 再抽 `AgentQueue`；09-09（§03ai）`SvcClient`（按服务发现建 HTTP 客户端）。**教训**：① 兜底 fallback 不能静默把"失败"变成"原样继续"（旧分卷缺依赖时原样返回整本）；② `cargo fmt --all` 曾把 64 个文件重排进提交——本仓库 Rust 不走 rustfmt，别跑。

### 03ba｜真机内存危机：流式优化（2026-09-19，真机通）

552MB《镖人》优化时 VmRSS 几十秒冲到 **1.4GB+**，可用内存探底约 25MB，抢在全系统 OOM 前手动叫停。根因：内存版优化整本读入；`MemoryMax=192M` 从未生效（systemd 没把 memory 控制器代理进 `system.slice`）。修法：两阶段流式；真机复测同书 VmRSS 全程 8–53MB。临时产物没点前缀会被列成条目 → 半成品一律点前缀。

### 03bh｜OOM 排查：落库不拆分路径叠 3 份（2026-09-19，真机通）

≤90MB 落库路径同时三份数据（整本读入 + 自检解压全部条目 + multipart 再克隆），估算峰值 180–270MB → 流式发送（线上字节逐字节相同）。**真机**：80MB 书 VmHWM 全程约 3.4MB。结论：book-serve 是唯一有实质 OOM 风险的服务，但**不拆服务**（函数级问题）。

### 03bi｜`imgopt` 无像素上限，几小时内真机撞上（2026-09-19，真机通）

第一轮《乱马1/2》VmHWM 271MB → 按"3 字节/像素"估算加 2500 万像素上限；第二轮《火影忍者》再撞 262MB——实测约 9–16MB/百万像素，是估算的 3–5 倍 → 改 900 万像素。**教训**：① "没有真实触发样本"的保质期很短；② 定内存阈值前必须先实测。

### 03bm｜耗电与日志全面核查（2026-09-20，真机通）

book-serve 空闲不耗电（夜间 0.2–0.5 秒/小时）；真问题是列表每次开 zip → `BufReader` + 按文件戳缓存，约快 70 倍（09-30 收编成 `rmsvc_core::cache::StampCache`）；wifi-watch 每 15 秒 fork 一串命令 → 链路正常只读 sysfs，约 9 倍；孤儿边车（设备上 28 个，同名新书会继承旧记录）→ 落地前清 + 启动 GC。**教训**：新增轮询字段必须缓存。

### 03bq｜book-serve 可靠性：panic=unwind、OpRegistry、启动恢复（2026-09-20）

`panic = "unwind"` 让后台线程的 `catch_unwind` 真能兜住 panic（此前 `abort` 下一次 panic 摔掉整个进程）；忙锁不落盘（重启 ＝ 没有操作还在跑；落盘反而会"永久卡忙"）；启动时 `recover_interrupted` 修正停在 `pending` 的记录。边界：`catch_unwind` 接不住栈溢出（SIGSEGV）。
